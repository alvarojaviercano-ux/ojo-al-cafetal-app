Overview

Eye on the Coffee Farm is a Flask application with server-rendered pages. It keeps its data in a relational database (PostgreSQL in production, SQLite for local work) and loads the trained models from files. The models are trained on my computer; the server only loads and uses them.

Data model

Eight tables: users, farms, plots, inspections, recommendations, feedback, event_log and settings. A user (grower) owns farms; a farm has plots; a plot has inspections; an inspection has recommendations and feedback. Each inspection stores the model result, the model version, the response time, the 26 features (JSON) and the technician review. Timestamps are saved in UTC and shown in Colombia time.

Roles and rules

  • Grower: sees and edits only their own farms, plots and inspections.
  • Technician: sees all farms, reviews inspections, answers feedback, sees monitoring and reports.
  • Administrator: everything above, plus users, event log and deleting inspections.
  • Self-registration always creates a grower. Only an administrator creates technicians and administrators, and cannot demote, disable or remove the last active administrator (including themselves).
  • Every POST form carries a CSRF token. Passwords are hashed. Forbidden attempts are written to the event log.
  • A user can make at most 40 inspections per hour.

Configuration (environment variables)

VariableUse
DATABASE_URLPostgreSQL connection string. If it is empty, SQLite (sistema.db) is used.
SECRET_KEYSession signing key. If empty, one is generated and saved in the database.
ADMIN_USER, ADMIN_PASSWORDCreate the first administrator at start (if it does not exist).
TECHNICIAN_USER, TECHNICIAN_PASSWORDCreate a technician account.
GROWER_USER, GROWER_PASSWORDCreate a grower with a demo farm and plot.

Passwords are never stored in the code or in the repository.

Run, test and deploy

  1. Local. pip install -r requirements.txt, then python app.py. Without DATABASE_URL it uses SQLite.
  2. Test. python selftest.py runs the full flow (registration, roles, farms, plots, inspection, review, actions, feedback, administration, monitoring) on a temporary database.
  3. Render. Create a PostgreSQL database, copy its internal URL to DATABASE_URL in the web service, set the account variables, and deploy with gunicorn app:app. Tables are created automatically at the first start.
  4. Health. /health checks the database and shows the model version.

Monitoring, incidents and maintenance

  • Monitoring page (technician, administrator): response time, errors, agreement with technicians, feedback, low confidence, doubtful cuts, drift and model versions.
  • Event log (administrator): logins, failed logins, inferences with milliseconds, errors, forbidden attempts and administrative actions.
  • Incidents: reported from Feedback; answered and resolved by staff. The administrator reviews the open ones every week.
  • Backups: use the automatic backups of the managed PostgreSQL plan, or pg_dump before changing the schema.
  • New model: train locally, replace the files in models/, push to GitHub, and check the Monitoring page. The version label changes automatically.
